Capturing Agent Reasoning

How Azri should ingest the context that diffs alone can't carry.

TL;DR

When an AI agent debugs a real bug, roughly four-fifths of the explanation value lives in the session — the SQL queries, the dead-ends, the architectural reasoning, the Oracle reviews — not in the final diff. Azri today sees only the diff, so its output ceiling is bounded by what code changes can reveal. To break the ceiling, the right architecture is layered ingestion: read every available signal (PR body, linked issues, commit messages, agent journal files, session transcripts, optional MCP feed), synthesize them into a unified reasoning context, then generate. The single highest-leverage building block is a small Azri Skill — a drop-in AGENTS.md / CLAUDE.md instruction that has any agent write structured entries to .azri/sessions/<branch>.md during work. That file is the bridge.

The Gap

why prompt-tuning won't fix this

The reference benchmark is a real explainer page rendered for a Balance AI bug-fix PR (BAL-187 / Process All stuck at 0/0). It runs about ten minutes of reading, with eleven distinct sections — TL;DR with prod-DB numbers, "cast of characters", seven-step investigation with SQL queries, before/after Mermaid flows, Oracle review feedback, open threads, lessons. Section by section, here's where the underlying content actually came from while the explainer was being generated:

No amount of prompt-tuning on top of the current input will close this gap. The fix is feeding Azri the same context the agent had during the work — that's the architectural conclusion.

Four Capture Mechanisms

what's actually possible in 2026, ranked by maturity

The research surfaced four mechanisms with real production examples. They differ wildly in maturity, agent coverage, and friction. None dominates the others — each fills a different niche.

Stable Tier 1 · 100% agent coverage

PR body + linked issues + commits

Already accessible via the GitHub API. Today Azri reads the PR body (truncated to 1000 chars in Stage 2) but doesn't follow Closes #N links and doesn't pass commit messages to Stage 3 section prompts.

Low ceiling — most devs don't write rich PR descriptions — but completely free. A baseline every other mechanism should sit on top of.

Effort: ~1 day · Free uplift

Stable Tier 2 · 100% agent coverage

Journal file via AGENTS.md / CLAUDE.md

Drop a rules-file snippet that instructs any agent to append structured entries to .azri/sessions/<branch>.md during work. The paper-trail project reports 12.6% of Claude Code output naturally flows into these files when properly instructed.

Best ceiling-to-effort ratio. Works across opencode, Cursor, Claude Code, and any future agent that respects rules conventions.

Effort: ~1 day · Highest leverage

Stable (CC + opencode) Absent (Cursor)

Direct session transcript

Claude Code stores JSONL at ~/.claude/projects/<hash>/<session>.jsonl including a ReasoningPart type. opencode exposes GET /session/:id/message with the same structured parts. Cursor has no programmatic equivalent — must fall back to MCP.

Passive: zero user effort once integrated. Noisy: every tool call shows up, dead-ends included.

Effort: ~3–4 days · 2/3 agents covered

Stable Tier 4 · 100% agent coverage

Dedicated MCP server

Ship @vdmkotai/azri-mcp exposing azri_start_session, azri_log_reasoning, azri_finalize. Agents call into it during work; the server accumulates structured JSON. Patterns proven by cursor-session-tracer, mcp-session-mgr, and similar projects.

Highest fidelity (structured data with parent-step references), heaviest infrastructure, and mostly redundant with Tier 2 unless we're chasing real-time multi-agent collaboration.

Effort: ~5–7 days · Defer until Tier 2 validates

Architecture: Layered Ingestion

read whatever is available; weight by fidelity

The right architectural answer is not picking one mechanism. It's reading whatever's available and weighting it. Azri adds a new pipeline stage — Stage 1.5, the Reasoning Synthesizer — that merges every available input into a unified ReasoningContext object before Stage 2 (structure) and Stage 3 (sections) see it.

Purple: new stage. Yellow: explicit override (highest priority). Blue: the killer feature — the journal file. The Reasoning Synthesizer is a single small LLM call that takes all available inputs and emits a normalized markdown context, capped to a token budget.

Source priority when inputs disagree or overlap

  1. Explicit narrative (--narrative file.md) — wins absolutely. If the user hand-wrote (or had an agent write) a markdown narrative, Azri renders it directly and skips auto-generation.
  2. MCP-structured entries — highest fidelity machine-readable source, when available.
  3. Journal file (.azri/sessions/<branch>.md) — agent-curated, very high signal.
  4. Session transcript — passive but noisy (includes every tool call, including dead-ends and retries).
  5. PR body + linked issues + PR review comments — human-written, often terse.
  6. Commit messages — useful for the reasoning arc when squash-merged commits are descriptive.
  7. Diff — always available, lowest standalone value but ground truth for what actually changed.

The Killer Feature: an Azri Skill

the smallest building block that closes most of the gap

A "skill" here means a tiny set of files — one rules instruction (AGENTS.md for opencode/Cursor, CLAUDE.md for Claude Code) plus a journal-format spec — that any agent loads into its persistent session context at start-up. The agent then writes structured entries to .azri/sessions/<branch>.md as it works, with no per-step tool calls and no extra infrastructure.

An example journal looks like this:

# Session journal — fix/bea-audit-gate

## 2026-05-22T13:45:00Z — Hypothesis #1: dispatch broken
- Investigated: does Bea actually receive events from Balance?
- Files read: backend/api/services/bea_reconciliation_routing.py:120-180
- Queries: SELECT COUNT(*) FROM bea_event_queue WHERE status='queued';
- Result: 0 queued, all picked up — dispatch works
- Verdict: ❌ disproved, move on

## 2026-05-22T14:31:00Z — Hypothesis #3: audit gate failing
- Investigated: why 85 events flipped to 'failed'
- Files read: bea_reconciliation_routing.py:720-739 (the gate)
- Queries: SELECT last_error FROM bea_event_queue WHERE status='failed' LIMIT 5;
- Result: "document event completed without terminal document state"
- Verdict: ✅ Confirmed — gate requires document.processed=True

## 2026-05-22T15:05:00Z — Oracle review caught 2 bugs in fix
- Bug 1: proposed type="low_confidence" but flag-document only accepts type="other"
- Bug 2: subcommand recommendation was ambiguous — LLM would pass entire phrase verbatim
- Action: rewrote wrapper to commit to one subcommand per call

When the skill instructs the agent to write

The skill spec defines explicit trigger conditions so journals don't become noisy dumps:

  • At session start — create the file with header (branch name, task description).
  • After each significant investigation step — a hypothesis was tested, a meaningful file was read, a decision was made.
  • After consulting a subagent — Oracle, librarian, explore, anything that produced new information.
  • After every dead-end — this is gold. Agents tend to suppress these. Explicit instruction to write them produces the most valuable entries.
  • Before commit — write a final summary entry tying everything together.
Why a skill and not a tool? A tool requires the agent to remember to call it on every step. A skill is loaded into the agent's persistent context at session start — it shapes behavior without per-step API surface. Lower friction, higher adoption. The skill conventions in opencode, Cursor, and Claude Code are mature enough in 2026 that this is the right level of abstraction.

Cost & Phasing

ship lowest-friction tiers first, validate, then invest

Five tiers ranked by effort-to-value. Recommended phasing: ship Tier 0 + Tier 2 first (~1.5 days combined), evaluate quality lift on real PRs, then decide whether Tier 3 transcript reading or Tier 4 MCP is worth the investment.

Tier Mechanism Effort Coverage Quality lift
0 --narrative file.md override ~0.5d opt-in Highest — matches Balance instantly if user provides a hand-written narrative
1 Linked issues + reviews + commit messages ~1d universal Low-medium · free baseline
2 Journal file via AGENTS.md skill ~1d any agent High · best ratio
3 Session transcript parser (CC + opencode) ~3–4d 2/3 agents High · passive capture
4 Dedicated MCP server ~5–7d universal Highest fidelity · heaviest infra
Strategic note. Tiers 0 and 2 alone already close most of the Balance-quality gap. Tier 4 (MCP) is impressive but mostly redundant with Tier 2 (journal) unless we're chasing real-time multi-agent collaboration. Don't build the MCP server until journal-file mode has validated user value.

Open Questions for Discussion

decisions to make together before committing to the build
  • Privacy & secrets. Session journals will contain code snippets, file paths, potentially API responses or SQL results. Should Azri redact patterns matching sk-*, ghp_*, JWT-shaped tokens, etc. before including them in the rendered page? Default-on or opt-in? What about per-file allow/deny lists?
  • Journal format: prose vs structured. The example above is markdown prose with section headers. An alternative is YAML/JSON entries — easier to parse, harder for agents to write naturally. A hybrid (markdown sections with structured frontmatter) is possible. Which optimizes for adoption?
  • Where does Stage 1.5 run? Before Stage 1 (so the summarizer also has reasoning context) or between Stages 1 and 2? The former is more powerful but roughly doubles the cost of every run. Maybe it should depend on whether journal data was actually supplied.
  • Failure mode: noisy journals. What if an agent writes 200 KB of low-signal entries? Truncation strategy: keep last N hypotheses + all entries marked verdict: ✅? A per-source token budget enforced by the Reasoning Synthesizer? Both?
  • Cross-PR reasoning. Sometimes the reasoning that produced PR N was developed during work on PR N-1 (refactor first, fix bug after; or an architectural insight from a sibling feature). Should journals optionally span branches?
  • Skill distribution. Drop the skill files via azri init? Publish as a separate package (@vdmkotai/azri-skill) installable via the platform's skill manager? Both? Versioning strategy when the journal format evolves?
  • Hosted reasoning store? Eventually, should the bot maintain a per-repo journal index so the team can grep across PRs, cluster related decisions, or surface recurring dead-ends? (Probably v2 — but worth flagging now so v0.2 file formats don't paint us into a corner.)
