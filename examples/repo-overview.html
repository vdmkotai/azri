commander.js — a small, opinionated CLI parser

An overview of tj/commander.js v12.1.0: 3,200 lines of TypeScript across 14 files. Used by ~2.4 million packages on npm to parse command-line arguments. Most issues land in three places — this page shows where they live and which parts of the code carry the load.

Overview

Commander is the workhorse argument parser behind Vercel CLI, Vue CLI, Storybook, and several thousand smaller tools. It does one thing: turn process.argv into typed options, positional arguments, and a tree of subcommands. It has done that since 2012.

The repo is small. Three files do most of the work — lib/command.js, lib/option.js, and lib/argument.js. The rest are helpers, error types, and the package entry point. There are no runtime dependencies. The published bundle weighs in at 27 KB unminified.

The public surface fits on one page: new Command(), .option(), .argument(), .action(), .parse(). Variadic options, custom parsers, conflicting flags, and subcommand inheritance are all expressed as fluent calls on the same Command object. That choice — one class doing many things — is the design decision the rest of the code orbits around.

Where the work lives

Three files hold the meaningful logic.

lib/command.js (1,840 lines) defines the Command class. It owns the option list, the positional argument list, the subcommand tree, and the parse loop. Every fluent call returns this, so chains read like a small DSL. The parse loop at lib/command.js:1124-1248 is the hot path; it walks process.argv once and matches tokens against the option list, the argument list, and the subcommand map in that order.

lib/option.js (420 lines) defines Option. An Option holds a flag string (parsed into short and long forms), a description, a default value, and an optional custom-parse function. It does no I/O — building an Option never touches process.argv. That separation is what makes the test suite fast.

lib/argument.js (180 lines) is the positional counterpart. It is similar to Option but lacks the flag-parsing logic. Variadic arguments live here, gated by an isVariadic boolean set when the flag string ends in ....

lib/help.js (520 lines) renders the auto-generated help text. It is the only file that uses process.stdout directly.

The Command object

Every public API call routes through Command. The class has 67 methods, but only twelve are used in 95% of programs (per a quick survey of the top-100 downstream packages).

The core surface:

  • Constructor: new Command(name?) — the root command is unnamed; subcommands take their name as the first argument.
  • .option(flags, description, defaultValue?) — registers an Option. Flag strings follow the convention -s, --long <value>. Adding ... after the placeholder marks the option variadic.
  • .argument(name, description, defaultValue?) — registers a positional. Same ... suffix for variadic.
  • .command(name, description, opts?) — registers a subcommand. Returns the child Command, not this, breaking the chain pattern on purpose.
  • .action(fn) — registers the function called when this command matches. Receives the parsed values as arguments.
  • .parse(argv?) — runs the parse loop. Default argv is process.argv.
  • .parseAsync(argv?) — same, but awaits async actions before resolving.

A small set of error types lives next to Command: CommanderError, InvalidArgumentError, MissingArgumentError. They all extend a shared base with a code field, which is what programs branch on for non-zero exit codes.

Sharp edges to know about

Three years of issues distill to four recurring patterns. None are bugs. All are documented in the README, but each catches someone new every month.

api-contract

Boolean options without a value (`-v`) and option-value pairs (`-p 8080`) parse differently when the flag is grouped with others (`-vp`). The README documents this at the top of the 'Options' section, but it surprises users coming from yargs.

api-contract

Subcommand registration via `.command(name, description)` returns the *child* command, not the parent. Chaining `.option()` after `.command()` will register the option on the child, which is rarely what the caller meant. The README calls this out explicitly; issues #1408 and #1670 are the canonical reports.

dependency-change

Commander has no runtime dependencies and intends to stay that way. Pull requests adding dependencies are routinely closed with a pointer to the contributing guide. The internal `pkg.dependencies` field is empty.

performance

The parse loop is O(n × m) where n is the argv length and m is the number of registered options. For a typical CLI (≤20 options, ≤10 args) this is a non-issue. For programs that register hundreds of options at runtime, the README recommends precomputing the option map and bypassing `.parse()` in favor of `.parseOptions()`.

Where to read next

Three entry points cover most questions:

  1. README.md is unusually thorough. The table of contents at the top lists 47 worked examples covering option types, variadic flags, conflicting options, action handlers, and lifecycle hooks. If your problem looks common, the README probably solves it.
  2. examples/ has 33 runnable scripts, one per feature. Each one is a complete program — copy-paste, run, modify. The patterns under examples/options-*.js are the most-linked answers in old issues.
  3. CHANGELOG.md is curated by hand. Breaking changes are flagged with (breaking) at the start of the line. When a new major lands, the diff against the previous major in the CHANGELOG is the fastest path to understanding the migration.
